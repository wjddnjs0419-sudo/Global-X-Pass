# 🚨 시니어 엔지니어 최종 코드 리뷰 (Post-Mortem)

**수신:** Claude (개발 에이전트)
**상태:** `PostDetailPage` SPOF 해체 및 P2(타입 안정성), P4(유틸리티 분리) 완료 직후
**목적:** 현재 코드베이스에 잔존하는 근본적인 기술 부채와 과잉 엔지니어링 리스크 팩트 폭격

---

## 🥶 총평: "폭탄을 쪼개서 여기저기 숨겨놨을 뿐, 뇌관은 그대로 꽂혀 있다."

SPOF(`PostDetailPage`)를 쪼개고 `any`를 잡은 것은 '마이너스 100점'을 '0점'으로 돌려놓은 기본 조치에 불과합니다. 
진행된 리팩터링은 표면적인 파일 분리에 그쳤으며, 본질적인 복잡도와 레거시 패턴은 그대로 다른 곳으로 이관되었습니다. 당장 내일 터지진 않겠지만, 3개월 뒤 기능 확장이나 디자인 개편 시 개발팀을 마비시킬 전형적인 **"가분수 아키텍처"**입니다.

아래 4가지 핵심 문제를 인지하고, 다음 작업 시 반드시 설계 방향을 수정할 것.

---

### 1. 근본적인 UI 아키텍처의 실패 (끝나지 않은 P3)
*   **현실:** `PLAN.md`에 명시된 바와 같이 "7개 섹션 컴포넌트에 총 137개의 인라인 스타일 블록"이 그대로 잔존.
*   **비판:** 프론트엔드 코드로서 낙제점. 컴포넌트를 분리했음에도 핵심 섹션들이 `style={{ display: 'flex', ... }}` 같은 인라인 스타일로 떡칠되어 있음.
*   **리스크:** 디자인 시스템의 중앙 통제가 불가능함. Tailwind나 CSS 모듈을 도입해 놓고 인라인을 방치하는 것은 유지보수성을 극도로 떨어뜨리며, 향후 반응형 패치나 테마 수정 시 막대한 공수를 유발함. **UI 클렌징(인라인 제거)이 시급함.**

### 2. 본질을 외면한 책임 회피 (Naver Import 로직)
*   **현실:** `buildNaverRenderModel`, `getNaverImportDiagnostics` 같은 거대한 파싱 괴물들이 `utils/htmlSecurity.ts`나 `postDetailModel.ts`로 위치만 이동함.
*   **비판:** 네이버 블로그의 DOM을 파싱하는 더러운 로직의 복잡도 자체를 줄이지 않고 방으로 숨긴 셈. 정규식을 기반으로 HTML을 클라이언트에서 뜯어고치는 방식은 극히 취약함.
*   **리스크:** 네이버가 DOM 구조를 변경하는 즉시 사이트 렌더링이 붕괴됨. 무거운 파싱과 정제는 데이터를 DB에 적재할 때(Server-side/Crawler) 1회만 수행해야 함. 클라이언트 렌더링 단에서 매번 이 연산을 수행하는 것은 설계 미스이자 성능 낭비임.

### 3. 스타트업 수준을 넘어선 과잉 엔지니어링 (Over-Engineering)
*   **현실:** 단순 포털 사이트에 Edge Function이 22개나 존재하며, 관리자 권한 체크에 DB RLS, JWT AAL2 검증, MFA 우회용 임시 테이블까지 동원.
*   **비판:** 대규모 트래픽의 금융권 서비스에나 어울릴 법한 과도한 보안/설계 오버스펙. 코드는 적을수록, 아키텍처는 단순할수록 장애가 안 남.
*   **리스크:** 신규 실무자가 인수인계를 받을 때 수직 절벽에 가까운 Learning Curve를 경험하게 됨. 작은 버그 하나를 잡기 위해 세션, RLS, 함수 로직을 모두 뒤져야 하는 '기술적 감옥' 상태.

### 4. 눈가리고 아웅식의 컴포넌트화 (`AttachmentPopover`)
*   **현실:** `AttachmentPopover`를 분리해 놓고, 정작 표준 UI 라이브러리(`shadcn/ui` Popover) 채택은 defer(보류)함.
*   **비판:** 파일만 나눴을 뿐, 내부 구현은 `useEffect`를 이용해 document에 이벤트 리스너를 직접 다는 바닐라 JS 레거시 패턴을 그대로 유지. 
*   **Action Required:** React의 선언적 패러다임에 맞게 `shadcn/ui` 등 검증된 툴을 사용하여 로직을 추상화할 것.
