# 🚨 시니어 엔지니어 최종 코드 리뷰 (Post-Mortem)

**수신:** Claude (개발 에이전트)
**상태:** `PostDetailPage` SPOF 해체 및 P2(타입 안정성), P4(유틸리티 분리) 완료 직후
**목적:** 잔존 기술 부채와 과잉 엔지니어링 리스크 폭격

---

## 🥶 총평: "폭탄 쪼개 숨겼을 뿐, 뇌관 그대로 꽂혀 있음."

SPOF(`PostDetailPage`) 쪼개고 `any` 잡음 = '-100점' → '0점' 기본 조치. 
리팩터링 표면적 파일 분리뿐, 본질 복잡도와 레거시 패턴 다른 곳으로 이관됨. 내일 안 터져도 3개월 뒤 기능 확장/디자인 개편 시 팀 마비시킬 전형 **"가분수 아키텍처"**.

4가지 핵심 문제 인지, 다음 작업 시 설계 방향 수정 필수.

---

### 1. 근본적인 UI 아키텍처의 실패 (끝나지 않은 P3)
*   **현실:** `PLAN.md` 명시대로 "7개 섹션 컴포넌트에 총 137개의 인라인 스타일 블록" 잔존.
*   **비판:** 프론트엔드 낙제점. 컴포넌트 분리해도 핵심 섹션 `style={{ display: 'flex', ... }}` 인라인 떡칠.
*   **리스크:** 디자인 시스템 중앙 통제 불가. Tailwind/CSS 모듈 도입하고 인라인 방치 = 유지보수성 극저하, 반응형/테마 수정 시 막대한 공수. **UI 클렌징(인라인 제거) 시급.**

### 2. 본질을 외면한 책임 회피 (Naver Import 로직)
*   **현실:** `buildNaverRenderModel`, `getNaverImportDiagnostics` 같은 파싱 괴물 `utils/htmlSecurity.ts`/`postDetailModel.ts`로 위치만 이동.
*   **비판:** 네이버 블로그 DOM 파싱 더러운 로직 복잡도 안 줄이고 방에 숨김. 정규식 기반 클라이언트 HTML 가공 극히 취약.
*   **리스크:** 네이버 DOM 바뀌면 렌더링 즉시 붕괴. 무거운 파싱/정제는 DB 적재 시(Server-side/Crawler) 1회만 수행해야 함. 클라이언트 렌더링 단 매번 수행 = 설계 미스, 성능 낭비.

### 3. 스타트업 수준을 넘어선 과잉 엔지니어링 (Over-Engineering)
*   **현실:** 단순 포털에 Edge Function 22개, 관리자 권한 체크에 DB RLS + JWT AAL2 검증 + MFA 우회용 임시 테이블까지 동원.
*   **비판:** 금융권 수준 과도한 보안/설계 오버스펙. 코드 적을수록, 아키텍처 단순할수록 장애 안 남.
*   **리스크:** 신규 실무자 인수인계 시 수직 절벽 Learning Curve. 작은 버그 하나 잡으려 세션/RLS/함수 로직 다 뒤져야 하는 '기술적 감옥'.

### 4. 눈가리고 아웅식의 컴포넌트화 (`AttachmentPopover`)
*   **현실:** `AttachmentPopover` 분리해놓고 표준 UI 라이브러리(`shadcn/ui` Popover) 채택은 defer.
*   **비판:** 파일만 나눔, 내부는 `useEffect`로 document에 이벤트 리스너 직접 다는 바닐라 JS 레거시 패턴 유지.
*   **Action Required:** React 선언적 패러다임 맞게 `shadcn/ui` 등 검증된 툴로 로직 추상화할 것.
